# Participant Entity

A participant is any person connected to a Work Audit session. Participants are stored on the session as a map keyed by socket connection ID.

> **Critical:** The facilitator is **NOT** stored in the `session.participants` map. Only engineer participants appear in that map. The facilitator's socket ID is tracked separately in `session.facilitatorId`, and their display name in `session.facilitatorName`. When the facilitator reconnects, the server updates `session.facilitatorId` to the new socket ID without creating any participant record. Any code iterating `session.participants` will only see engineers — the facilitator is always excluded. UI that shows participant counts, rosters, or activity breakdowns by participant must not add a separate check for the facilitator, because the facilitator is simply never in the map.

---

## Field Reference

| Field | Type | Default | Required | Description |
|---|---|---|---|---|
| `id` | String (socket ID) | Set at join time | Yes | The socket connection ID assigned to this participant at the moment they joined the session. Socket IDs are generated by Socket.io and are opaque strings. Because they change on browser reload or network reconnection, `id` is not a stable identity key — `name` is. The `id` is used as the map key in the session's `participants` map and as the `participantId` on activities submitted by this participant. |
| `name` | String | None | Yes | Display name entered by the engineer on the join screen, or the facilitator's name entered at session creation. The name is the stable identity key used for reconnection. Two participants with the same name are treated as the same person by the reconnection logic. Names are not validated for uniqueness at join time beyond the reconnection rebinding check, but it is recommended that UI surfaces warn users if their chosen name is already in use by an active connection. |
| `role` | Enumeration | `IC` | Yes | The participant's role within their team. One of: `IC`, `EM`, `PM`, `UX`, `Other`. Set at join time. See [enumerations.md](./enumerations.md) for role descriptions. Defaults to `IC` (Individual Contributor) if not specified. |
| `joinedAt` | Timestamp (ISO 8601) | Set at join time | Yes | The date and time when this participant joined the session. Set once and never modified. Used for display in the participant roster and for determining join order when assigning colors. |
| `color` | String (hex color) | Assigned at join | Yes | A hex color string assigned to this participant from a fixed palette of 8 colors. The server picks the first palette color not already in use by another participant; if all 8 are taken, it falls back to cycling by join count modulo 8. The color is used to visually identify this participant's activities throughout the session UI, including in the activity card, the merged-activity multi-author display, and the matrix scatter plot. |
| `initials` | String (1–2 characters) | Derived from name | Yes | A short abbreviation derived from the participant's name. See "Initials Derivation Rules" below for the full algorithm. Examples: "Marco Reyes" → "MR", "Alice" → "AL", "Bob Smith Jones" → "BJ", "Jean-Pierre Dupont" → "JD". Used in activity cards, merged-activity author chips, and the participant roster. |
| `isFacilitator` | Boolean | `false` | Yes | True if and only if this participant is the session facilitator. Exactly one participant in the session has `isFacilitator: true`. Engineers always have `isFacilitator: false`. This flag controls which operations the server permits for this participant's socket connection. |

---

## Color Palette

The fixed color palette contains exactly 8 colors, cycled in join order. The palette is chosen to be visually distinguishable and to work on both light and dark backgrounds. The exact hex values are defined in the server-side constants (`AVATAR_COLORS`); the spec requires only that:

- There are exactly 8 distinct colors in the palette.
- Colors are assigned in a fixed order, not randomly.
- Assignment is based on join order: the server picks the first color in the palette not already in use; if all 8 are used, it falls back to cycling by `participants.size % 8`.
- After 8 participants, the palette wraps around and the 9th participant receives the same color as the 1st.

## Initials Derivation Rules

Initials are computed deterministically from the participant's name at join time. The algorithm is:

1. Trim leading and trailing whitespace from the name.
2. Split the trimmed name on whitespace (spaces, tabs). Hyphens and apostrophes that are part of a word do not act as split points — only whitespace splits.
3. **Single-word names (exactly 1 word after split):** return the first 2 characters of the word, uppercased. If the word is only 1 character, return that 1 character. Do **not** use the first character of the word alone — always take 2 characters for single-word names.
4. **Multi-word names (2 or more words after split):** return the first character of the FIRST word concatenated with the first character of the LAST word, uppercased. Middle words are **always ignored**, regardless of how many words there are. For example: a 3-word name returns `firstWord[0] + lastWord[0]`, not `firstWord[0] + secondWord[0]`.
5. If the name is empty or blank after trimming, the behavior is implementation-defined.

> **Implementation note:** A common mistake is to take the first character of every word and slice to 2 — this produces wrong results for 3+ word names ("Bob Smith Jones" → "BS" instead of "BJ") and wrong results for single-word names ("Alice" → "A" instead of "AL"). The algorithm must branch on word count first.

Examples:

| Name | Result | Reason |
|---|---|---|
| Marco Reyes | MR | First of first ("M") + first of last ("R") |
| Alice | AL | Single word — first 2 chars of "Alice" |
| Bob Smith Jones | BJ | First of "Bob" + first of "Jones" (last word; "Smith" is ignored) |
| Jean-Pierre Dupont | JD | First of "Jean-Pierre" + first of "Dupont" (hyphen doesn't split) |
| mary anne | MA | First of "mary" + first of "anne", uppercased |
| O'Brien | O' | Single word — first 2 chars: "O'" (apostrophe included) |

## Reconnection Behavior

Because socket IDs are ephemeral, the system uses the participant's display name as the stable identity key for reconnection. The reconnection logic applies in the following situations:

- An engineer reloads their browser tab.
- An engineer's network connection drops and is restored.
- The facilitator's browser tab reloads (the facilitator token is also checked).

### Engineer Reconnection

When a new socket connection attempts to join a session and provides a name that already exists in the session's `participants` map (comparison is **case-sensitive** — `"alice"` and `"Alice"` are treated as different names):

1. The system identifies the existing participant record with that name.
2. The old socket ID is removed from the `participants` map; the participant record is re-keyed under the new socket ID.
3. The participant record's `id` field is updated to the new socket ID.
4. All activities whose `participantName` matches the reconnecting engineer's name have their `participantId` updated to the new socket ID, so that subsequent ownership checks (for edits and deletes) continue to pass.
5. The client receives the full current session state, including their own previously submitted activities.
6. Other connected clients are notified that the old socket left (`participant:left` with old ID) and a new participant joined (`participant:joined` with new ID).

The engineer does not need to re-enter their name if it is stored in `localStorage`. The join screen reads from `localStorage` and pre-fills the name field; if the name matches an existing participant and the session status permits joining, reconnection proceeds automatically.

### Facilitator Reconnection

When a connection presents the `facilitatorToken` matching the session's `facilitatorToken`:

1. The system recognizes this as the facilitator reconnecting.
2. The `facilitatorId` on the session is updated to the new socket ID.
3. The participant record for the facilitator (identified by `isFacilitator: true`) has its `id` updated to the new socket ID and is re-keyed in the `participants` map.
4. All facilitator permissions are restored immediately.
5. The client receives the full current session state.

### No Duplicate Records

Reconnection must not create a new participant record when an existing record with the same name is found. The system rebinds the existing record to the new socket rather than inserting a second entry.
